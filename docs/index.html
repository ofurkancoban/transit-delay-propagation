04 · Diagnosis

Why no model beats the operator yet

  • Re-slicing the test split by how fresh the operator's own prediction was shows LightGBM already matches or beats the operator outside a narrow "volatile" regime (delay actively changing right now, 2.2% of rows). The entire aggregate gap concentrates there: LightGBM's error is >10x the operator's in that slice alone.
  • Five volatility features engineered from existing TripUpdates history (delay_jump_1, delay_recent_std, delay_vs_route_recent_gap, etc.) were tried and adopted — a real ~0.5% overall improvement, but only ~0.1% on the volatile regime specifically, confirming the gap there is structural, not a tuning shortfall.
  • A live pull of the primary feed confirmed zero VehiclePosition entities are published, so whatever lets the operator react instantly is internal to the agency's own systems and not exposed here.
  • ServiceAlerts collection went live 2026-07-24 21:54 CEST as the next candidate signal (real disruption alerts — construction, technical problems, police activity — mixed with boilerplate attribution notices), delta-compressed by alert_id. Not yet tested against the model: history only starts accruing from deployment time forward.

07 · Feed limits

Feed limitations found so far

  • vehicle_id is never populated on the primary feed (0 of 9.09M realised stop-events, confirmed against the raw protobuf). The vehicle-chain / block propagation channel cannot be estimated from this source.
  • direction_id is always the GTFS-RT "unset" sentinel (-1) in realtime, and the static trips.txt omits direction_id/block_id entirely. "Same route and direction" network features reduce to "same route" only, joined via trip_id.
  • Two brief upstream feed-side stalls (2026-07-23 16:05-16:11, 2026-07-24 09:42-09:52) inflated lag_s but never took the collector process down; excluded from the realisation panel per pitfall 6.
  • Both findings are documented in README.md and constrained the edge-type ablation above.
